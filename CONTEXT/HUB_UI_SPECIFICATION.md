# EcliptOS Marketplace UI Specification

## Overview

This document specifies the requirements and implementation plan for building a custom UI for a forked MLRun functions repository. The UI will provide a user-friendly interface similar to [MLRun Hub](https://www.mlrun.org/hub/) for browsing, searching, and discovering custom functions, modules, and steps.

**Project Name**: EcliptOS Marketplace  
**Framework**: Next.js with Tailwind CSS  
**Initial Hosting**: Local development  
**Future**: Option C (Full-Stack) or Docker deployment  
**Timeline**: ASAP prototype - prioritize speed over optimization

## Project Goals

- Create a modern, card-based UI for browsing marketplace functions
- Provide search and filtering capabilities
- Enable easy discovery and integration of functions
- Maintain compatibility with MLRun's marketplace structure
- Keep initial implementation simple and maintainable

---

## Architecture: Option B - Custom Frontend (Primary)

### Overview

A client-side only application that reads from the built marketplace's `catalog.json` file and renders a modern, interactive UI. This approach prioritizes simplicity, fast deployment, and low maintenance overhead.

### Architecture Diagram

```
┌─────────────────┐
│   Static Host    │
│  (GitHub Pages/  │
│  Netlify/Vercel) │
└────────┬─────────┘
         │
         ├─── index.html
         ├─── catalog.json (from marketplace build)
         ├─── functions/
         │    └─── [function-name]/
         │         └─── latest/
         │              └─── static/ (docs, examples)
         └─── assets/
```

- **Next.js** (with static export for Option B, can upgrade to full SSR for Option C)

**Styling:**

**Hosting:**

### Core Features

#### 1. Function Discovery (v1 - Match MLRun Hub)
- **Card-based grid layout** displaying functions/modules/steps (exactly like [MLRun Hub](https://www.mlrun.org/hub/))
- Each card shows:
  - Function name (as heading)
  - Type badge (functions/modules/steps)
  - Kind badge (Job, Serving, Monitoring Application, etc.)
  - Description (full or truncated)
  - Categories (as tags/badges)
  - Last updated date ("Updated X ago")
  - Click to view details (or direct links to docs)

#### 2. Search & Filtering (v1 - Match MLRun Hub)
- **Global search bar** - "Q Search..." placeholder, search by name/description
- **Category filter sidebar** - Checkboxes for all categories (Audio, Data Analysis, etc.)
- **Kind filter sidebar** - Expandable sections:
  - Functions (Job, nuclio:serving, Serving)
  - Modules (Generic, Monitoring Application)
- **Sort dropdown** - "Sort by: Title (A-Z)" and "Title (A-Z)Last Modified" options
- **Result count** - "X results" display
- **Filter persistence** - Keep filters active when searching

#### 3. Function Details (v1 - Simplified)
- **Detail view** (can be modal or separate page - choose simplest):
  - Full description
  - Metadata (version, categories, kind)
  - Links to:
    - Documentation (if available)
    - Source code (if available)
    - Example notebook (if available)
  - Copy-to-clipboard for import command: `import mlrun\n\nfn = mlrun.import_function('hub://function_name')`
- **Note**: For v1, we can skip version history and detailed YAML views - focus on core browsing experience

#### 4. User Experience
- **Responsive design** - Works on desktop, tablet, mobile
- **Fast loading** - Optimized assets, lazy loading
- **Smooth interactions** - Transitions, loading states
- **Accessibility** - WCAG 2.1 AA compliance
- **SEO-friendly** - Meta tags, semantic HTML

#### 5. Navigation
- **Header** with:
  - Logo/branding
  - Navigation links
  - Search bar (persistent)
- **Footer** with:
  - Links to documentation
  - Repository link
  - License information

### Data Source

The application reads from:
- `catalog.json` - Main metadata file (generated by marketplace build)
- Structure: `{ "functions": { "master": { "function_name": { "latest": {...} } } } }`
- Static HTML files in `functions/[name]/latest/static/` for documentation

### Styling Guidelines

- **Color Scheme**: Customizable theme (primary, secondary, accent colors)
- **Typography**: Modern, readable font stack
- **Spacing**: Consistent spacing scale
- **Cards**: Subtle shadows, rounded corners, hover effects
- **Buttons**: Clear hierarchy (primary, secondary, tertiary)
- **Responsive Breakpoints**: Mobile (< 768px), Tablet (768-1024px), Desktop (> 1024px)

### Performance Considerations

- **Lazy Loading**: Load function details on demand
- **Code Splitting**: Split routes/components
- **Image Optimization**: Compress and use modern formats
- **Caching**: Leverage browser caching for catalog.json
- **Bundle Size**: Keep initial bundle < 200KB (gzipped)

## Future Development: Option C - Full-Stack Application

### Overview

A full-stack application with a backend API and database, enabling advanced features like user authentication, analytics, favorites, and dynamic content management.

### When to Consider Option C

- Need for user accounts and personalization
- Analytics and usage tracking requirements
- Admin dashboard for content management
- API endpoints for external integrations
- Real-time updates and notifications
- Advanced search with indexing
- User-generated content (ratings, reviews)

### Additional Features (Option C)

#### Backend API
- RESTful API endpoints
- GraphQL option for flexible queries
- Authentication (JWT, OAuth)
- Rate limiting and security
- Caching layer (Redis)

#### User Features
- User accounts and profiles
- Favorites/bookmarks
- Usage history
- Personal collections
- Notifications

#### Admin Features
- Content management dashboard
- Analytics dashboard
- User management
- Function approval workflow

#### Advanced Search
- Full-text search (Elasticsearch)
- Faceted search
- Search suggestions/autocomplete
- Search analytics

### Technology Stack (Option C)

**Backend:**
- **FastAPI** (Python) or **Express.js** (Node.js) or **Next.js API Routes**
- **PostgreSQL** or **MongoDB** for data persistence
- **Redis** for caching
- **Elasticsearch** for advanced search (optional)

**Frontend:**
- Same as Option B, but calls API instead of reading JSON directly
- State management (Redux, Zustand, or Context API)
- Authentication handling

**DevOps:**
- Docker containerization
- CI/CD pipeline
- Monitoring and logging
- Database migrations

### Migration Path from Option B to Option C

1. **Phase 1**: Keep existing frontend, add minimal backend API
2. **Phase 2**: Migrate data fetching to API calls
3. **Phase 3**: Add authentication layer
4. **Phase 4**: Implement user features
5. **Phase 5**: Add admin features

## Integration with Marketplace Build

### Build Process

1. Run marketplace build: `python -m cli.cli build-marketplace ...`
2. Copy/symlink generated files to UI's public directory:
   - `catalog.json`
   - `functions/` directory structure
   - `modules/` directory structure
   - `steps/` directory structure
3. Deploy UI with marketplace assets

### Automation

- **CI/CD Integration**: Automatically build marketplace and deploy UI
- **GitHub Actions**: Build on push to main branch
- **Deployment**: Auto-deploy to hosting platform
